# 超分辨率 / 画质增强 方案

先说结论：

- **服务端实时超分：直接排除**（无 GPU + 上行 2.86 Mbps，一路 1080p 就吃满）
- **AI 超分（Real-ESRGAN / Real-CUGAN）：只能离线，成本极高**，不适合作为播放链路
- **着色器放大（FSR / Anime4K）：客户端实时，可行且推荐**，这是唯一能给出「开着不卡」体验的路径

---

## 0. 先搞清楚「超分」的三种含义

| 类型 | 代表 | 算力 | 实时性 | 效果 |
| --- | --- | --- | --- | --- |
| **A. 着色器放大** | AMD FSR 1.0 (EASU+RCAS)、Anime4K | 极低，手机 GPU 够 | ✅ 实时 | 边缘更锐、纹理更实，但不是「无中生有」 |
| **B. AI 超分** | Real-ESRGAN、Real-CUGAN、waifu2x | 高，需要 GPU | ❌ 离线 | 真的能补细节，尤其动画/动漫脸 |
| **C. 服务端转码增强** | ffmpeg + libplacebo / 各家 SR | 服务器 GPU | ❌ | 同 B，且要占带宽 |

**用户要的「超分」体感上接近 B，但只有 A 能实时。** 这个落差必须说清楚。

---

## 1. 为什么 B 和 C 不可行（算清楚）

### 服务端实时（C）

- VPS 没有 GPU；CPU 上跑 Real-ESRGAN 一帧 1080p 要秒级，实时（24fps）需要 ~24 倍算力
- 就算跑得动，转码后的流仍然要从这台 2.86 Mbps 的机器发出去，1080p 都紧张，4K 更不可能

### 离线 AI 超分（B）

- 一部 2 小时影片，CPU 上 Real-ESRGAN 1080p→4K 大约要 **几天**
- 租 GPU 实例（如 A10/T4）约 1–3 小时/部，成本几元到十几元/部，还要存 4K HEVC（8–15GB/部）
- 做完之后**还是发不出去**（带宽）
- 唯一合理形态：**离线超分 + 下载到本地看**（和我们刚设计的下载功能结合）。但那时候手机上播放的是已经超分好的文件，
  本质是「转存服务」，不是「超分功能」

**结论：B/C 只有在「你愿意为少量收藏片花几小时/几块钱」时才有意义，不是通用功能。**

---

## 1.5 FSR / DLSS 到底能不能用

这两个名字经常被混为一谈，实际差得很远：

| 技术 | 类型 | 需要什么 | 视频播放能用吗 |
| --- | --- | --- | --- |
| **FSR 1.0**（EASU + RCAS） | 空间放大，纯 shader | 只要当前帧 | ✅ **可以，就是本方案** |
| FSR 2.x | 时间放大（TAA 式） | 运动矢量 + 深度 + jitter 矩阵 | ❌ 视频解码拿不到这些 |
| FSR 3 / 4 | 时间放大 + 补帧 / ML | 同上，FSR4 还要 RDNA4 硬件 | ❌ |
| **DLSS 2/3/4** | 时间放大 + 补帧，ML | **NVIDIA RTX 硬件 + 专有 SDK（NGX）+ 游戏引擎 G-buffer** | ❌ 完全不可能 |

### 为什么 FSR 2/3 和 DLSS 用不了

时间类超分的核心是「**用上一帧 + 运动矢量把历史像素重投影到当前帧**」。
运动矢量是**游戏引擎渲染时顺手输出的**（每个像素的屏幕空间位移），深度缓冲同理。

而视频播放拿到的是解码后的 YUV 帧：**没有运动矢量、没有深度、没有 jitter 矩阵**。
浏览器 / WebView 也没有任何 API 能把这些东西拿出来。

理论上可以从码流里反解 H.264/HEVC 的运动矢量，但：
- 浏览器和 Android 都不暴露解码器内部的 MV
- 就算拿到，压缩码流的 MV 是「编码块」粒度的，跟渲染用的逐像素 MV 不是一回事

**所以这条路是断的，不是「难」，是「数据不存在」。**

DLSS 还多两层门槛：必须有 NVIDIA RTX 硬件（tensor core），且要链接 NVIDIA 的专有运行库。
WebGPU / WebGL 里没有、也不会有这个接口。

### 但「DLSS for video」是真实存在的

**NVIDIA RTX Video Super Resolution（RTX VSR）** —— 这才是视频版的 AI 超分：

- 跑在**驱动层**，不在网页代码里，所以不占我们的实现成本
- 需要 NVIDIA RTX 显卡 + Windows + 支持的浏览器（Chrome / Edge）
- 在 NVIDIA 控制面板里打开即可，网页侧零改动

也就是说：**如果用户有 RTX 显卡，用 Chrome 看我们的站，可能白赚一个 AI 超分**。
我们唯一能做的是在设置里加一句提示，告诉他去开。
（macOS 没有对应物；AMD/Intel 有类似的驱动级视频增强，但覆盖面小得多。）

### 想要 DLSS 级画质，唯一诚实的路径

**离线 AI 超分**：把片子下载下来，用 Real-ESRGAN / Real-CUGAN 跑一遍（租 GPU，1–3 小时/部），
再播放超分后的文件。这不是「播放器功能」，是「转存服务」——见 §1 的成本分析。

### 顺便澄清一个常被混淆的概念

很多人说「超分」，其实想要的是**更流畅**，那是**补帧（VFI）**，不是超分：

| | 解决什么 | 代表 |
| --- | --- | --- |
| 超分 | 分辨率低、糊 | FSR / Real-ESRGAN |
| 补帧 | 帧率低、卡顿感 | RIFE / SVP / 电视 MEMC |

补帧在浏览器里也能做（光流插帧），但代价大得多，且运动场景容易出现鬼影/果冻效应。
本方案只做超分，补帧单独立项。

## 2. 推荐方案 A：客户端着色器放大（WebGL2）

### 为什么放在 Web 端而不是原生

APK 是 WebView 壳，**Web 端实现一次，浏览器和 App 同时得到**。
如果放原生（Media3 GlEffect），就要维护两套，且 Web 端永远没有。

### 技术选型

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| **FSR 1.0（EASU + RCAS）** | AMD 开源，两个全屏 pass，边缘自适应放大 + 锐化 | ✅ 首选，真人内容效果好、开销小 |
| **Anime4K** | 专为动画设计，GLSL 有 WebGL 移植 | ✅ 本项目有 `kind=anime`，动画内容单独用它，效果明显 |
| **WebGPU 计算着色器** | 可以跑轻量 NN | ⚠️ Android WebView 支持不完整，先不用 |
| **CSS `filter: contrast/saturate`** | 零成本 | ❌ 只是调色，不是超分，可作为一个独立开关 |
| **Canvas2D + `ctx.filter`** | 简单 | ❌ 1080p 下明显掉帧 |

### 实现结构

hls.js 解码到 `<video>`，我们把视频帧搬进 WebGL 纹理，用着色器放大后画到 `<canvas>`：

```
<video> (hls.js 解码, 隐藏但继续播放)
   ↓ requestVideoFrameCallback 逐帧
texImage2D(gl, video)            ← 浏览器走 GPU 零拷贝
   ↓ pass 1: EASU（边缘自适应放大）
   ↓ pass 2: RCAS（对比度自适应锐化）
   ↓
<canvas> 叠加在视频位置，按屏幕实际像素输出
```

关键点：

- **输出尺寸 = min(屏幕物理像素, 源尺寸 × 2)**。手机屏幕 1080p 时，720p 源放大到 1080p 正好；
  再大就是浪费 GPU（人眼也看不出）。
- **用 `requestVideoFrameCallback` 同步**，不要用 `requestAnimationFrame` 硬刷，否则会重复/丢帧。
- 只在该开启时创建 WebGL 上下文，关掉就 `gl.deleteXxx` 回收，避免长期占显存。
- 全屏播放我们用的是自己的 `.nf-player` 覆盖层（不是浏览器 Fullscreen API），
  所以 canvas 可以正常铺满，不受限制。
- 我们的 `Player.tsx` 已经在 `art.on('video:timeupdate')` 里拿到时间轴，
  再接一个 `video.requestVideoFrameCallback` 循环即可，**不动播放内核**。

### 档位设计（建议）

| 档位 | 做什么 | 开销 |
| --- | --- | --- |
| 关 | 原生播放，零开销 | 0 |
| 轻（默认） | 只做 RCAS 锐化，不放大 | 很低，1080p 源也能开 |
| 强 | EASU 放大 + RCAS | 中，看源尺寸和屏幕 |
| 动画 | Anime4K | 中，动画内容收益最大 |

**默认应该是「轻」**：对已经 1080p 的源，单做锐化的观感提升就已经很明显，而且几乎不掉帧。

### 自动降级（必须有）

- 连续 3 秒平均帧率 < 45 → 自动降一档并提示一次
- 源本身 < 480p 或码率极低 → 提示「源太糊，超分只会放大噪点」并默认关闭

## 3. 一个反直觉但重要的点：低码率源超分会**更难看**

采集源普遍是「高分辨率 + 低码率」，块效应和蚊式噪声很明显。
锐化会把压缩瑕疵一起放大，看起来比不处理还糟。

所以正确的处理顺序是 **轻降噪 → 放大 → 锐化**，而不是直接锐化。
FSR 的 RCAS 自带一定的瑕疵抑制，但对重度压缩的源仍不够。
如果要认真做，第一遍 pass 加一个很轻的边缘保持降噪（比如 bilateral 的廉价近似）。

**判断标准**：开超分后如果出现「噪点更明显 / 色带更严重」，就说明这个源不该开。

## 4. 需要先做的实验（决定要不要投入）

和下载功能一样，先花 30 分钟验证，再决定做不做：

1. **WebView 里 `texImage2D(video)` 是否走 GPU 零拷贝**
   - 真机（不是模拟器，模拟器是软件渲染，帧率毫无参考价值）
   - 测法：1080p 播放，开 WebGL 直通（不做任何处理），看帧率和 CPU 占用
   - 如果直通就掉帧 → 说明 WebView 的视频帧回读很贵，方案 A 在 App 里不成立，
     退化为「只在浏览器做」或「App 内用原生 GL」
2. **手机屏幕实际分辨率**：很多手机 `devicePixelRatio` 是 3，但视频输出到 canvas 用 1080p 就够
3. **A/B 观感**：同一帧截图对比，肉眼能不能看出差别（这决定了值不值得做）

## 5. 落地顺序

| 阶段 | 内容 | 估计 |
| --- | --- | --- |
| P0 | 真机实验：WebGL 直通帧率 + 一眼能不能看出效果 | 0.5 小时 |
| P1 | 「轻」档：RCAS 锐化（单 pass，代码最少，收益/成本最高） | 0.5 天 |
| P2 | 「强」档：EASU 放大 + 自适应输出尺寸 + 自动降级 | 1 天 |
| P3 | 动画档：Anime4K（按 `kind=anime` 自动推荐） | 1 天 |
| P4 | 轻降噪前置（针对低码率源） | 0.5–1 天 |

---

## 6. 和另外两个功能的关系

- **和下载功能**：下载到本地的文件播放时同样可以套用同一套着色器（都在 Web 播放器里），零额外成本。
- **和一起看**：超分是纯本地后处理，不影响时间轴同步，可以放心共存。
  但要注意**开启超分会增加单帧耗时**，弱网成员本来就容易卡，缓冲协同会更频繁触发。

---

## 7. 需要拍板

1. **默认档位**：我建议默认「轻」（只锐化），用户可手动升到「强」
2. **要不要做动画专用档**（Anime4K）—— 你的库里 `kind=anime` 内容占比如何？
3. **是否接受「只在浏览器生效、App 内降级」**：如果真机实验发现 WebView 回读视频帧太贵，
   这是唯一务实的退路（否则要在 APK 里写一套原生 GL，工作量翻倍）

---

## 8. 一句实话

对绝大多数采集源来说，**画质的瓶颈是源本身，不是放大算法**。
同样一部片，选对线路（我们已有 `/api/quality` 探测分辨率/码率）带来的提升，
往往比任何超分算法都大。

所以如果只做一件事：**先把「自动选最高画质线路」做扎实**，再谈超分。
超分是锦上添花，不是雪中送炭。
