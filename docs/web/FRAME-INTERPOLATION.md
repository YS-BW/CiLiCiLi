# 补帧（帧率提升 / VFI）方案

先说结论：

- **实时客户端补帧：不建议做**。没有运动矢量，必须自己算稠密光流，手机 WebView 上做不到「比不补更好看」。
- **最正确且零成本的解法是「匹配刷新率」**，不是补帧。这个我们能在 APK 里做。
- **真补帧只适合离线**（下载 → RIFE → 50fps 文件）。

---

## 0. 问题到底出在哪：25fps 遇上 60Hz

实测我们的源（取真实分片解密后 ffprobe）：

```
codec_name=h264   profile=High
width=1920  height=1080
r_frame_rate=25/1   avg_frame_rate=25/1
bit_rate ≈ 1711 kbps（2.07s 分片 441KB）
```

**25 fps 是 PAL 制**，国内采集源基本都是这个帧率。而屏幕是 60Hz / 120Hz：

| 屏幕刷新率 | 每帧显示周期 | 结果 |
| --- | --- | --- |
| 60 Hz | 2.4 | 不规则（2,2,3,2,3…）→ **横移镜头抖动** |
| 120 Hz | 4.8 | 同样不规则 |
| **50 Hz** | **2.0** | **完全均匀，零抖动** |

这个抖动（judder）是「低帧率感」的主要来源，比「帧数少」本身更刺眼。

---

## 1. 第一优先：匹配刷新率（不是补帧）

**如果屏幕能切到 50Hz（25fps 的整数倍），每帧正好显示 2 次 → 抖动彻底消失，零计算、零画质损失。**

Android 原生侧完全做得到：

```java
Display display = getWindowManager().getDefaultDisplay();
for (Display.Mode m : display.getSupportedModes()) {
    // 找 refreshRate 最接近 fps × 整数倍 的模式
}
getWindow().setAttributes(lp);   // lp.preferredDisplayModeId = 选中的模式
```

- API 23+，`preferredDisplayModeId`
- 很多旗舰机支持 24 / 25 / 30 / 48 / 50 / 60 / 120 多档模式
- 这正是「影院模式 / 真 24p」的原理
- **浏览器里做不到**（没有 API 改屏幕刷新率），只有原生能做

**补帧是「用算法模拟 50fps」，刷新率匹配是「让屏幕真的按 25fps 显示」——后者是零瑕疵的。**
所以顺序必须是：先做刷新率匹配，再考虑要不要补帧。

### 代价与风险

- 切刷新率会让屏幕闪一下（部分机型），播放页进入时切、退出时切回
- 少数机型在低刷新率下触控采样率会降，影响进度条拖动体验 → 需要在播放页锁定、退页恢复
- 需要真机验证机型覆盖情况

## 2. 真补帧（VFI）三条路

### A. 实时客户端补帧 —— 不推荐

核心障碍和超分一样：**没有运动矢量**。

| 步骤 | 代价 |
| --- | --- |
| 稠密光流估计（Farnebäck / DIS） | 多 pass（10+ 次全屏采样），1080p 在手机 GPU 上做不到 50fps |
| 双向 warp + 遮挡处理 | 遮挡区域（新出现/被遮住的像素）会撕裂或鬼影，运动越剧烈越明显 |
| 合成 | 相对便宜 |

结果：**要么掉帧（比不补还差），要么鬼影明显（观感更糟）**。
WebView 里还多一层限制：`texImage2D(video)` 的回读成本未知（见超分文档 §4 的实验）。

### B. 离线补帧（RIFE）—— 质量最好，和下载功能结合

```
下载 → RIFE / SVFI / Flowframes 插到 50fps → 播放
```

- GPU 上 1080p 每帧几十毫秒 → 2 小时影片约 **10–30 分钟**
- 输出 50fps 体积约翻倍（1.7 Mbps → ~3 Mbps），或换更好的编码压回去
- 质量远好于实时方案（模型更大、可以多帧输入）
- **这是「真补帧」唯一能看的路径**

和下载功能天然结合：用户下载后跑一遍脚本，得到 50fps 版本。我们可以提供一个现成脚本/一键命令。

### C. 借外部设备（最省事）

| 方案 | 说明 |
| --- | --- |
| 电视 MEMC | 中高端电视都有，效果通常不错 |
| mpv + SVP | 桌面最成熟的方案 |
| PotPlayer + SVP | Windows 常见组合 |

我们只负责把片子下载下来，补帧交给它们。**零开发成本。**

## 3. 如果一定要在 App 里做实时，最低成本的降级方案

**帧混合（crossfade）**：两个纹理 `mix()`，一个 pass，几乎零成本。

- 效果：运动重影/拖影，像「糊了一层」
- 绝大多数人觉得**比抖动更难受**（尤其看片，不是玩游戏）
- 唯一勉强能用的场景：静态镜头 + 轻微抖动

而且「只在横移镜头时启用」需要检测镜头运动 → 又要算光流 → 绕回 A 的问题。

**结论：不建议做。**

---

## 4. 一个被低估的成本：我们目前探测不到帧率

- **HLS 播放列表不含 fps**（我们的 master 里连 `FRAME-RATE` 属性都没有）
- hls.js 的 `levels[]` 只有宽高/码率，没有帧率
- 浏览器也没有「获取源帧率」的 API

要知道 fps，只能**解析 H.264 的 SPS（VUI timing info）**：

| 位置 | 可行性 | 成本 |
| --- | --- | --- |
| 后端 Go | 自己写 SPS 解析（bit reader + exp-golomb），约 150–200 行 | 中，但一次做好全局可用 |
| 前端 JS | 同上，约 150 行，需要先拿到分片字节（又要过代理/直连） | 中 |
| APK 原生 | `MediaExtractor` 对 TS 流不一定给 `KEY_FRAME_RATE` | 不确定 |

**务实做法**：后端在画质探测（`/api/quality`）时顺带解析一次 SPS，把 `fps` 存进结果并缓存
（按 `sourceKey + vodId + episode` 缓存 30 天）。这样前端拿到 fps 就能选刷新率。
成本：解析一个分片（约 400KB）+ 一次 SPS 解析，1–2 秒，且可缓存。

**但后端镜像里没有 ffmpeg**（只有静态二进制），所以只能自己写 SPS 解析，不能调 ffprobe。

---

## 5. 建议的落地顺序

| 阶段 | 内容 | 估计 |
| --- | --- | --- |
| P0 | 后端加 SPS 帧率解析，`/api/quality` 返回 `fps` | 0.5–1 天 |
| P1 | APK：按 fps 选 `preferredDisplayModeId`，播放页进入切、退出恢复 | 0.5 天 |
| P2 | 真机 A/B：切刷新率前后对比，确认抖动确实消失（也可能发现大部分人本来就不在意） | 0.5 小时 |
| P3 | 离线补帧脚本（RIFE）+ 文档，配合下载功能 | 0.5 天 |
| — | 实时客户端补帧 | **不做** |

---

## 6. 和另外几个功能的关系

- **超分**：两者都是本地后处理，可以叠加。但**同时开启时单帧耗时叠加**，弱网成员在「一起看」里更容易触发缓冲协同。
- **一起看**：补帧/刷新率都是本地行为，不影响时间轴同步。但如果做刷新率切换，**全员切换时机不同**会让画面节奏短暂不一致（不影响进度）。
- **下载**：离线补帧的前置条件。

---

## 7. 需要拍板

1. **先做刷新率匹配还是直接跳过补帧**？我建议先做刷新率匹配，很可能做完就不需要补帧了。
2. **要不要投入 SPS 帧率解析**（0.5–1 天）—— 不做的话，刷新率匹配只能靠用户手动选，或者默认按 25fps 猜（国内源大概率对）。
3. **离线补帧脚本要不要做**（0.5 天，纯脚本 + 文档）

---

## 8. 一句实话

「补帧」在视频播放里是**投入产出比最低**的画质功能：

- 实时方案在移动端做不好，做了大概率更难看
- 离线方案质量好，但用户得愿意等、愿意多占一倍存储
- 而**刷新率匹配**这个几乎零成本的手段，能解决同一个问题（抖动）的 80%

先做刷新率匹配，做完再看要不要补帧 —— 很可能就不需要了。
