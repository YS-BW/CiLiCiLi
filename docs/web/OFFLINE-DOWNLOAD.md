# 视频下载 / 离线观看 方案

先说结论：**能做，但只有「APK 原生下载」这一条路能给出好体验**。
Web 端想直接下，绕不开 VPS 那 2.86 Mbps 上行，1GB 的片子要占满带宽近 50 分钟。

---

## 0. 为什么这件事比想象中难

我们的播放链路是：**客户端直连 CDN 拉 m3u8 + 分片**，后端只做 m3u8 改写和兜底代理。
下载要解决的是同一个问题的另一面：

| 障碍 | 说明 |
| --- | --- |
| **CORS** | 浏览器 fetch CDN 分片会被跨域拦死，必须走 `/api/proxy` → 吃 VPS 带宽 |
| **VPS 上行 2.86 Mbps** | 走代理下载 ≈ 300 KB/s 上限，1GB ≈ 55 分钟，且期间别人看片会卡 |
| **CDN 反爬** | 我们在 VPS 上用 Go 直连 CDN 被 403 过（TLS 指纹被识别），客户端直连是否被拦要实测 |
| **HLS 不是单文件** | 分片要按序拉、TS 直接拼、fMP4 要带 init 段、AES-128 要解密 |
| **贴片广告** | 广告就在码流里，下下来会带着（可以用 `contentOffsetMs` 丢掉开头几个分片） |

好消息：现有代码已经有一半基础设施 ——
`internal/m3u8` 会改写 `#EXT-X-KEY` / `#EXT-X-MAP` 的 URI（加密流本来就能播），
`internal/quality` 能探测各线路的分辨率/编码，`/api/proxy` 支持 Range。

---

## 1. 四条路径对比

| 路径 | 谁在拉流 | 速度 | VPS 压力 | 手机一键 | 成本 |
| --- | --- | --- | --- | --- | --- |
| **A. APK 原生下载** | 手机直连 CDN | CDN/手机上限（很快） | **零** | ✅ | 2 天 |
| **B. Web 导出 yt-dlp 命令** | 用户电脑直连 CDN | 最快 | 零 | ❌ | 半天 |
| **C. Web 浏览器内下载** | 经 `/api/proxy` | ≈300 KB/s | **打满上行** | ✅ | 半天 |
| D. VPS 下载转存后提供 | VPS | 下行快、上行慢 | 打满上行 | ✅ | 2 天+ |

**推荐：A 为主 + B 兜底，C 只对小文件限流开放，D 不做。**

---

## 2. 路径 A：APK 原生下载（推荐）

WebView 里做不了（CORS + 后台会被暂停），必须在原生侧做。这也是 APK 壳相对纯 Web 的
第一个**真正的独占价值**。

### 流程

```
详情页「下载」按钮
   ↓ JS 桥 downloadEpisode({sourceKey, vodId, episodeId, m3u8, referer, ua, title, epName})
原生 DownloadService（前台服务 + 通知栏进度）
   ↓ 解析 master m3u8 → 选最高码率 variant（可直接用 /api/quality 的探测结果）
   ↓ 逐个拉分片（Range/断点续传；失败重试 + 指数退避）
   ↓ 加密流：EXT-X-KEY METHOD=AES-128 → 拉 key → AES/CBC/PKCS7 解密
   ↓ TS：直接按序拼接；fMP4：先写 EXT-X-MAP 的 init 段再拼
   ↓ 写入 MediaStore.Downloads（Android 10+ 免权限）或 app 私有目录
完成通知（点击可播放 / 分享）
```

### 关键实现点

- **前台服务**：`FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` 权限，通知栏显示进度，
  否则息屏就断。这是必须的，也是唯一需要新加的权限。
- **断点续传**：每个任务一个 `.json` 记录已完成分片下标 + 总大小，重试只补缺口。
  手机上网络切换（WiFi↔5G）非常频繁，没有续传基本没法用。
- **保存位置**：`MediaStore.Downloads`（用户能在「文件」里看到，不用权限）；
  或 app 私有目录 + 系统分享（更隐蔽，卸载即删）。
- **CDN 反爬**：必须带 `User-Agent` / `Referer`（从播放时的请求里带过来）。
  如果 Java 的 TLS 指纹也被 403，退化方案：分片改走 `/api/proxy`（慢但一定能成）。
  **这一点要先做 30 分钟的实验再决定架构**，别写完才发现拉不动。
- **贴片广告**：下载时把前 N 个分片丢掉（N 由房间/影片的 `contentOffsetMs` 决定），
  或者提供一个「跳过片头秒数」输入。注意丢分片会导致时间轴偏移，播放器需要重新 seek。
- **多线路**：默认选 `/api/quality` 探测出的最高分辨率线路；也允许用户在详情页选。
- **批量**：下载队列 + 并发上限 2（并发太高反而被 CDN 限速），支持整季批量。

### 为什么它值得做

- 完全不占 VPS 带宽，速度取决于 CDN 和手机网络，通常比在线看还快
- 真正离线：地铁、飞机、弱网都能看
- 顺带解决「源站抽风/熔断」导致看不了的问题

**这是 APK 存在的最强理由之一。** 现在 APK 相对浏览器几乎没有独占能力，下载是第一个。

## 3. 路径 B：Web 端导出下载命令（零成本，建议一起做）

详情页加一个「复制下载命令」，后端返回一条现成命令：

```sh
yt-dlp -f best \
  --referer "https://采集站域名/" \
  -H "User-Agent: Mozilla/5.0 ..." \
  -o "%(title)s - 第01集.mp4" \
  "https://cdn.xxx/20261024/abc/index.m3u8"
```

- 用户在电脑上粘一下就能下，速度是本地直连 CDN，最快，还能自动转封装成 mp4
- **后端零改动**：只要能拿到最终 m3u8 地址 + 必要的 Referer/UA（这些播放时本来就有）
- 缺点：要装 yt-dlp；手机上一键不了

成本大概半天，收益是「任何设备都能拿到离线文件」，性价比很高。

---

## 4. 路径 C：Web 浏览器内下载（限流开放）

技术上是 `fetch` 分片 → 拼 Blob → `a[download]`。但：

- 必须走 `/api/proxy` 绕 CORS
- VPS 上行 2.86 Mbps → 1GB 影片约 55 分钟，**期间你自己在线看片会卡**

所以要么不做，要么严格限制：

- 只对时长 < 5 分钟 / 体积 < 100MB 的开放（短剧、短片正好）
- 全局同时只允许 1 个下载任务，并对该任务限速（比如 1 Mbps）
- 界面上明说「大文件请用 App 下载」

---

## 5. 路径 D：为什么不做「VPS 下载转存」

看着很诱人（CDN→VPS 是下行，通常 100Mbps+，拉得飞快），但卡在最后一步：
**从 VPS 发给用户仍然只有 2.86 Mbps**。等于把慢的地方从「用户→CDN」搬到「VPS→用户」，
还多占一份磁盘和 ffmpeg 依赖（镜像 +80MB）。

唯一有意义的变体是「云转存到网盘」——VPS 下完直接传阿里云盘/115，用户从网盘下载。
但那要对接各家网盘 API、处理登录态和限速，是另一个量级的工程，且不稳定。

## 7. 需要拍板

1. **下载文件放哪**：系统「下载」目录（用户可见，能被别的播放器打开）／app 私有目录（更隐蔽，卸载即删）／两者都支持
2. **是否要整季批量下载**（会影响队列和存储管理的复杂度）
3. **贴片广告**：默认跳过开头广告，还是保留（有些人反而想留着）
4. **Web 端要不要路径 C**（我倾向只做 B，把 C 留给短视频）

## 8. 可行性实验（已跑，结论：可行）

原本担心的风险是「Java 的 TLS 指纹被 CDN 识别 → 403」。实测下来风险不在 TLS，在**地区封锁**。

### 实验一：Java 走完整下载链路（成功）

用 Java 17 的 `HttpURLConnection`（和 Android 原生侧同一套 API）跑了一遍
「master → variant → key → 分片 → AES-128 解密」：

```
master        : 119 字节
variant       : .../1863kb/hls/index.m3u8
variant 大小  : 261156 字节
分片数        : 4814
key           : 16 字节 (HTTP 放行)
首分片(密文)  : 34224 字节
首分片(明文)  : 34216 字节
TS 同步字节   : ✅ 0x47 对齐，是合法 MPEG-TS
```

**结论：Java 原生侧拉流 + 解密完全可行**，不需要 ffmpeg，不需要走 `/api/proxy`。
一集 1080p 约 4800 个分片、估算 160MB 左右。

### 实验二：地区封锁是真实存在的（比 TLS 更致命）

拿 6 个源的首集 URL 从同一个出口（非大陆）请求：

| 源 | 域名 | 结果 |
| --- | --- | --- |
| dyttzy | play.phimgood.com | 403 |
| ffzy_tv / ffzy5 / ffzy_cj | super.ffzy-online6.com | 403 |
| hongniu | hn.bfvvs.com | 200（但返回 HTML 分享页） |
| jszy | vj.jisuzyv.com | 200（但返回 HTML 分享页） |

403 的响应体写得很明确：

```html
<h1>403 Forbidden</h1>
<p>The region has been denied.</p>
```

**所以下载功能必须做「直连失败 → 走 /api/proxy」的自动回退**，不能假设客户端一定能连上 CDN。
这一点播放器已经这么做了（`Player.tsx` 里 direct → proxy 回退），下载器要照抄。

### 实验三：两个坑（手写下载器最容易翻车的地方）

1. **`#EXT-X-KEY` 是按分片生效的，不是全局的。** 真实播放列表长这样：

   ```
   #EXT-X-KEY:METHOD=AES-128,URI="key.key",IV=0x000...
   #EXTINF:2, /W1PQ5bbG.ts        ← 加密
   ...
   #EXT-X-KEY:METHOD=NONE
   #EXTINF:2, /xxxxx.ts           ← 不加密（插播段）
   #EXT-X-KEY:METHOD=AES-128,...
   ```

   同一份列表里 AES-128 和 NONE 交替出现（4800 个分片里有 12 处 KEY 切换）。
   下载器必须**逐分片记录当时的密钥状态**，不能「取第一个 KEY 就全局套用」——
   我自己的第一版探针就踩了这个坑，解出来不是 TS。

2. **分片请求必须带 `Referer`，否则 CDN 返回「HTTP 200 + 16 字节『资源不存在!』」。**

   这是最毒的一个坑：状态码是 200，只看 `getResponseCode()` 会以为成功，
   结果存下来一个 16 字节的坏文件。实测：

   ```
   curl <segment>                        → HTTP 200, 16 字节  "资源不存在!"
   curl -e "https://<host>/" <segment>   → HTTP 200, 441808 字节  合法分片
   ```

   所以下载器**必须做内容校验**，不能只看状态码：
   - MPEG-TS：首字节 `0x47`，且第 188 字节也是 `0x47`
   - fMP4：`ftyp` box
   - 体积下限（比如 < 1KB 直接判定失败）
   - 校验失败 → 带 Referer 重试 → 仍失败才报错

3. **不是所有源都给真实 m3u8。** hongniu / jszy 返回的是 HTML 分享页，需要 JS 提取器才能拿到
   m3u8（这类源在 Web 端本来就播不了）。所以下载按钮要按「能否解析出真实 m3u8」来决定是否可点，
   拿不到就禁用并提示，而不是让用户下到一堆 HTML。
